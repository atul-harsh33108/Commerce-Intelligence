01

What was built

Two halves that meet at a warehouse. A transactional platform on PostgreSQL — nine Spring Boot services, each owning its own database — and an analytical read path on MySQL that a Python agent queries in English. Nothing crosses between them by a database connection; only by change events.

The data is real. Olist is a Brazilian marketplace that published 100,000 anonymised orders, and every count in this document was produced by loading those CSVs, not by generating plausible ones. That matters more than it sounds: several bugs here were only reachable with real data, because synthetic data is too well-behaved.

Spring Cloud Gateway Eureka Config Server Resilience4j Transactional outbox Choreographed saga Debezium CDC Star schema LangGraph NL→SQL Qdrant Zipkin tracing Prometheus + Grafana

Three ground rules shaped every decision. Spring-native only — no Spring Cloud Alibaba, because the job market this targets asks about Eureka and Gateway. Two database engines, deliberately — PostgreSQL for transactions, MySQL for the warehouse, because a cross-engine gap is what makes change-data-capture necessary rather than a copy job. And never provision cloud resources: the AWS equivalents are mapped in the docs and the Kubernetes manifests are written, but nothing in the repository creates a billable thing.

03

The one lesson, nine times

Nine separate bugs across this project shared a single shape: a check that confirmed something was running rather than that it worked. Each one passed the check that was actually being performed, and failed the thing the check was supposed to be about.

That pattern is the most useful thing the project produced, and it is worth stating before the individual bugs, because the individual bugs are only interesting as instances of it.

The thing that looked fineWhat it was actually doing
Debezium connectors reporting RUNNINGProducing nothing — topic auto-creation was disabled
A CDC sink consuming happilyNever committing on a quiet stream
An Elasticsearch index with 32,951 documentsBuilt by dynamic mapping; every annotation silently ignored
A Redis cache at 100% hit rateEvery hit throwing ClassCastException
A benchmark reporting −23% p50 latencyTiming HTTP 500s, which are fast
kubectl apply --dry-run=client passingQuietly contacting a cluster that only existed on my laptop
13 integration tests passingUsing a Redis that nothing in the test config declared
docker compose ps all healthyGateway unreachable from the host it ran on
depends_on: service_started satisfiedContainer existed; process could not yet serve

The corollary that changed how I write scripts

A measurement instrument that cannot fail is not a measurement. cache_benchmark.py caught HTTPError, read the body to keep the connection tidy, and returned the elapsed time anyway. It would have reported the same improvement against a service that returned 500 to everything — and for four steps, that is exactly what it did. It now refuses to report a latency for any batch that was not entirely HTTP 200.

04

The problems, in order of what they cost

A cache in which every hit failed — and two instruments that agreed it was fine

Step 6Looked healthy
Symptom
First read of a product: 200. Every read after: 401 "Authentication required" — on a public endpoint, for a full ten-minute TTL.
Cause
GenericJackson2JsonRedisSerializer's no-argument constructor enables the default typing that writes @class. Passing your own ObjectMapper uses it exactly as given, so nothing recorded the type and every read came back a LinkedHashMap. A cache miss worked; a cache hit threw. The precise inverse of a cache.
Hidden by
Three things at once. The benchmark timed error responses. Redis's own hit counter counts lookups, not usable values. And /error was not permitted in the filter chain, so Spring's internal error forward was rejected and the 500 was rendered as a 401 — wrong status, wrong reason, wrong subsystem.
Found by
Opening the storefront in a browser. React StrictMode double-invokes effects in development, so the product page fetched the same product twice. Four steps of curl never did, because curl asks once.
Fix
One typed serializer per cache rather than re-enabling default typing — which would let the deserialiser instantiate whatever class name it finds in Redis. Plus the benchmark now checks status, and all six services permit /error. Step 6's published numbers were corrected: 98.8% of queries removed, not 99.6%.

Spring's self-invocation trap

Step 5
Symptom
"no transaction is known to be in progress", twice a second, forever.
Cause
The outbox relay's @Scheduled method called its own @Transactional method. Spring's proxy only intercepts calls arriving from outside the bean, so an internal call bypasses it entirely and the annotation does nothing.
Fix
Split into two beans — OutboxRelay owns the timer, OutboxPublisher owns the unit of work. The call now crosses a proxy boundary.

An index that was 80% working

Step 7Looked healthy
Symptom
q=computr → 30 hits (fuzzy matching worked) but q=health beauty → 0 hits, against 32,951 indexed documents.
Cause
@Document, @Setting and @MultiField describe an index; they do not create one. Calling save() against a missing index lets Elasticsearch create it first by dynamic mapping, and every annotation is silently dropped. Single-word queries worked because the default analyser handles them — so the service looked healthy, and I had already written "search works" in my notes.
Also learned
Underscore is not a word boundary to the standard tokenizer, so health_beauty is one token and needs a char_filter — which must run before tokenisation. All 71 Olist categories are underscore-joined. And an analyser cannot be altered in place: there is no ALTER, only delete, recreate, reindex.
Fix
Create the index explicitly with createWithMapping(), and log an error at startup if an existing index's settings do not mention the analyser. Three lines that would have replaced half a day.

27% of the warehouse pointing at "Unknown"

Step 8Real data only
Symptom
30,635 of 112,652 facts had no geography — invisible until the real dataset was loaded.
Cause
A late-arriving dimension. geography_id is derived from the customer's state, and it was resolved once, at the moment the fact was built — when the customer row was still a stub with no state yet.
Fix
A reconcile_geography() pass after dimensions settle. 30,635 → 2.

A documented command that had never been run

Step 12
Symptom
docker compose --profile apps up -d appeared in the README and in the compose file's own header. There was no apps profile. It starts the databases, starts no service, and reports success — Compose does not warn about a profile nothing declares.
Cause
Written at Step 0 and wrong from that moment. Nothing caught it in twelve steps because the platform was always started the other documented way, so the broken command was never the one anybody typed.
Fix
An actual profile, verified by stopping every host JVM first so a service answering could not have been the old process. Also found --profile obs advertised in the same comment block, where the profile is called observability. Every profile named anywhere is now checked mechanically.

A config change that did nothing, twice, for two different silent reasons

Step 10
Symptom
Two metadata fixes applied to the agent, and the evaluation score did not move at all.
Cause
Two independent causes stacked. conf/ is COPYed into the image, so host edits were invisible to the running container. And behind that, a warm Redis retrieval cache — 717 keys — was serving the old answers anyway.
Fix
Mount the config read-only instead of baking it in, and flush the retrieval cache (database 1, never database 0) in the rebuild script. Accuracy then moved 78.8% → 97.0%.

The trace stops at the broker — and four healthy-looking traces are worse than none

Step 13
Symptom
One order produced four disconnected traces, each of which looked perfectly healthy on its own. "What happened to this order" had no answer.
Cause
A trace context lives on a thread. The outbox exists precisely to move publishing off the request thread — different thread, different transaction, up to 500 ms later — so the relay's scheduled tick starts a fresh trace and every downstream consumer attaches to that instead.
Fix
Store the W3C traceparent in the outbox row and re-open a span parented to it before publishing. Not the easier fix of copying the header onto the record: Spring Kafka injects one during send() too, and a record with two traceparent headers is honoured differently by different consumers.
Bonus
Restoring the context produces a visible outbox publish span, so the pattern's cost stops being an argument and becomes a gap you can measure — ~250 ms of a 608 ms saga is waiting for a relay poll.

What continuous integration found on its first three runs

The pipeline had been written at Step 12 and never executed, because the project's rule was local commits only. When the repository went public it ran for the first time — and failed three times in a row, each time on something that could not fail on the machine that wrote it.

RunFailureWhy it passed locally
1 ./mvnw: Permission denied (exit 126) Git tracks the executable bit; Windows filesystems do not. Fixed with git update-index --chmod=+x, the only way to set it from Windows.
1 failed to download openapi: connection refused kubectl --dry-run=client is not offline — it fetches the schema from an API server. It passed here only because a kubeconfig pointed at Docker Desktop. Replaced with kubeconform -strict, which also rejects unknown fields the dry run accepts.
2 All 13 catalog tests error in ~1 ms Broken since Step 7. A @Value placeholder lived only in the config server, which the test profile deliberately never reads. Unnoticed because every build in between was -DskipTests, while the docs displayed "13 tests, 0 failures" with a five-step-stale date.
3 Unable to connect to Redis, 5 of 13 @Cacheable means every read path does a cache lookup. A Redis container from docker compose was always listening on 6379, so the tests used a service nothing declared. Fixed with a Redis testcontainer — and verified by stopping the local one first.

What the AWS deployment found

Four more, all of which passed locally and in CI, because all four were claims that stopped being true away from one machine.

  • CORS origins hardcoded to localhost. A storefront on any real host fails every preflight, with a browser console message naming neither the gateway nor the deployment.
  • A required-variable guard made every other profile undeployable. The agent declared ${GEMINI_API_KEY:?}, and Compose interpolates the whole file before reading profiles — so --profile apps, which involves no agent, refused to start. The evidence had been in the repository for weeks: CI passed dummy-for-validation to work around our own guard, and nobody asked why.
  • context: .. in an override file. Compose resolves relative paths against the project directory, not the override that declares them — discovered after four minutes spent building the nine images that came first.
  • depends_on: service_started is not readiness. The gateway launched when config-server's container existed rather than when it could serve, exhausted ~21 s of retry backoff, and exited 1. Compose then refused to start five dependents, so the visible symptom pointed at the last thing to fail instead of the first.

And one that belonged to the host, not the project

Deployment
Symptom
The site served traffic perfectly from the internet and was unreachable from the machine running it. Every container healthy; the smoke test could not connect.
Evidence
curl -6 [::1]:30080 → 200
curl -4 127.0.0.1:30080 → refused
Cause
The host previously ran k3s. systemctl disable --now k3s stops the service and leaves its netfilter state entirely intact — 510 KUBE-/CNI-/FLANNEL iptables rules plus live cni0 and flannel.1 interfaces, which intercepted Docker's IPv4 loopback publishing.
Fix
k3s-killall.sh, which k3s ships for exactly this, then a Docker restart so it reinstalls its own rules. Stopping a service does not undo what it did to the host.

The rest, briefly

  • Double JSON encoding. A producer used JsonSerializer while the relay already sends serialised JSON, so the broker received a JSON string containing JSON. The visible symptom was a missing dead-letter topic, two layers away from the cause.
  • KafkaAdmin silently ignores a List<NewTopic> — it must be KafkaAdmin.NewTopics. Three dead-letter topics did not exist, and each poison message blocked for 60 s.
  • A list in two Spring Cloud Config sources does not merge. Profile beats specificity, so a per-route override replaced the entire route table and every /api/** path 404'd.
  • The edge stricter than the services it fronts — three separate times. Three paths were public in a service and missing from the gateway's allowlist. Three bugs from one duplication is where duplication stops being acceptable.
  • auto.create.topics.enable=false blocked Debezium. Connectors RUNNING, producing nothing.
  • Elasticsearch stops counting at 10,000. The storefront showed "10,000 matches" against a 32,951-document index. Every query measured in Step 7 returned fewer than that; browsing with no query at all was the case too simple to have been measured.
  • Three scripts asserted outcomes without checking their preconditions — buying two units of a product with one in stock, then reporting the saga's correct compensation as a failure.

The agent — execution accuracy, and where the failures actually were

33 questions across eight categories, each with hand-written gold SQL. Scoring is execution accuracy: run both queries, compare result sets — column names and order ignored, row order ignored unless the question is a ranking. Two questions were reworded after the first run; the header of questions.yaml records that no question was changed because the model got it wrong.

RunCorrectAccuracyWhat changed
Baseline26 / 3378.8%—
After failure analysis32 / 3397.0%5 of 7 baseline failures were my metadata, not the model

The self-correction loop fired on 0 of 33 questions, so it was provoked deliberately with a question the schema cannot answer. It hallucinated SELECT AVG(age) FROM customers, validation rejected it, and the third attempt returned NULL rather than inventing a number. Two correction cycles, observed rather than assumed.

Streaming, observed in a browser for the first time

Until the storefront existed, the documentation said the server-sent-event path had never been consumed by a browser — a Python client reads the same frames but cannot tell you when they arrived. Eighteen progress events from one question, timestamped on arrival, spread across 17.3 seconds rather than delivered at the end. That is the evidence that the gateway is not buffering, and it also showed for the first time that the agent's three recall branches run concurrently — all three start within 141 ms of each other and finish 8 s apart.

Why 4 vCPU turned out to be a floor, not a preference

The same host had been running a comparable Spring Cloud project under k3s on 2 vCPUs. It reached 0 of 20 pods ready after 17 minutes, with 65+ restarts and a load average of 21 — and it was not memory: MemoryPressure=False, zero OOM kills. Nine JVMs starting simultaneously do not merely start slowly; each is too slow to answer its own health probe, the supervisor kills it, and the restart makes contention worse. The deploy script starts infrastructure first and waits for health, which helps and is not a substitute for cores.

07

What still does not work

Kept deliberately, because a list of features is a claim and a list of failures is evidence that the thing was actually run.

  • Twelve units of stock are held against cancelled orders. Their release events were dead-lettered and nothing re-reads a dead-letter topic. The reservation sweeper is written and unwired.
  • The agent smuggles refusals through the result channel. Asked for a measure the warehouse does not have, it returns SELECT 'Error: ...' — valid SQL whose single row is a sentence. A caller cannot distinguish that from an answer. The fix is in the agent's prompt, and the project's rule is to integrate rather than fork it.
  • Only geography is reconciled. Any other fact column derived from a dimension attribute has the same late-arrival exposure.
  • The Kubernetes manifests have never been applied to a cluster. 44 objects, schema-checked offline with kubeconform -strict, which says the schema is right and nothing about whether the platform would come up.
  • The JWT signing key still lives in the config repository. Fine on a laptop; the first thing that must move on any real deployment.
  • No end-to-end browser test in CI. The storefront build is checked; its behaviour is not.

What I would do differently

Write the smoke test before the third service, not after the fifth. Every bug in the "edge stricter than the services" family was found by it in seconds, and each had been sitting there since the moment the route was added.

And stop trusting any check that cannot fail on my own machine. Three of the last four bugs were exactly that — a validation step that needed a cluster I happened to have, a test using a Redis I happened to be running, a benchmark timing errors because it never read a status code.

Every figure on this page was produced by a script in the repository and is reproducible from a clean checkout. Where a number was later found to be wrong — Step 6's cache figures — the original is left visible above the correction rather than quietly replaced.
